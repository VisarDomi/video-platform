# Proposed HLS Timeline Architecture

Date: 2026-05-11

## Goal

Make `.ts` segment identity and edit cuts derive from one authoritative server-owned `playlist.m3u8`, not from frontend global scaling between browser duration and playlist duration.

## Design

Use `playlist.m3u8` as the only timeline artifact. The correct duration clock is media timeline duration, not MPEG-TS container `format.duration`.

Core responsibilities:

- Parse existing `playlist.m3u8` into structured segments and header state.
- Probe segment media timing with `ffprobe` when needed.
- Prefer byte-level MPEG-TS PTS parsing for `.ts` files and reserve ffprobe for fallbacks.
- Rewrite `#EXTINF` directly in `playlist.m3u8`.
- Recompute `#EXT-X-TARGETDURATION` directly in `playlist.m3u8`.
- Publish playlist changes atomically with temp file + rename.
- Surface validation/probe problems in logs and API responses instead of hiding them in another file.

## Ownership Rules

- Downloader owns active live playlist append while recording and writes media-duration `#EXTINF` for new segments.
- Server `PlaylistAuthority` owns historical/batch repair of finalized playlists.
- Server orphan finalizer may call `PlaylistAuthority` if it rebuilds playlists, but must not invent a different duration rule.
- Edit service derives from source playlist entries. Once old source playlists are repaired and new downloads are correct, edits inherit the canonical clock.
- HLS route remains read-only: it serves the published playlist and never heals on request.

This keeps one serializer and one canonical artifact for finalized and edited VODs.

## Implementation Phases

### Phase 1: Measurement and Guardrails

- Done: frontend logs playlist duration, native duration, seekable end, current segment, native-ended verdict, and remaining playlist time.
- Done: target video proved format-duration playlists can be about `120s` longer than video timeline.
- Done: terminal logs changed from early-ended rejection to confirmed playlist end after media-timeline rewrite.

Acceptance:

- For one known mismatch file, the report prints playlist sum, ffprobe sum, media duration from logs, and max per-segment duration delta.

### Phase 2: PlaylistAuthority Core

- Done: structured parser/serializer preserves segment metadata and `#EXT-X-DISCONTINUITY`.
- Done: atomic temp-file rename publication.
- Done: byte-first `.ts` probing reads PES PTS timestamps for adjacent media timeline durations.
- Done: bounded ffprobe fallback remains for tail/discontinuity cases bytes cannot fully define.
- Done: repair summaries include changed counts, missing/probe failures, total duration delta, and target duration.

Acceptance:

- Serializing an existing playlist without duration correction is byte-equivalent where possible, or structurally equivalent in tests.
- Corrected playlist target duration is `ceil(max(segment.duration))`.
- Interrupted writes do not leave partial `playlist.m3u8`.

### Phase 3: Future Writer Path

- Change downloader `MediaValidator` so Tango/FC2 accepted segments report video stream duration first, audio stream duration second, and format duration only as fallback.
- `PlaylistManager` already owns playlist append and target-duration updates, so this fixes future playlist writes at the owner rather than adding a later repair patch.
- Keep batch repair separate for old playlists.

Acceptance:

- New finalized VOD playlists are serialized by `PlaylistAuthority`.
- `video-server` logs include duration source and probe count.
- Probe failures are visible in logs and cause a warning/error result, not silent fallback metadata.

### Phase 4: Historical Repair Engine

- Add `POST /api/videos/repair-playlists?provider=tango&scope=all|downloads|edited`.
- Engine walks playlist folders one at a time to avoid heavy parallel CPU usage.
- It logs start/finish totals and per-playlist repair summaries.

Acceptance:

- Edited folders get their own canonical `playlist.m3u8`.
- Edited `playlist.m3u8` is generated by `PlaylistAuthority`, not string filtering.
- Existing fMP4 edit test covers `EXT-X-MAP` preservation.

### Phase 5: Edit Path

- Current edits derive playlist rows from the source playlist. This is acceptable after historical repair and future writer fix.
- If editing old unrepaired originals later becomes common, route edit-derived playlist serialization through `PlaylistAuthority` too.

Acceptance:

- Same frame no longer shows different `.ts` names because the UI uses the canonical playlist source.
- Logs distinguish canonical playlist time, browser media time, and hls.js loaded/decoded fragment identity.

### Phase 6: Remaining Hardening

- Add unit tests for `PlaylistAuthority` parser/serializer and discontinuity handling.
- Consider caching probe results by file path, size, and mtime if batch repair becomes repeated work.
- Consider hls.js fragment events if exact decoded-fragment identity is needed around boundaries.

Acceptance:

- Migration can run on one provider or one filename.
- It reports changed playlists and empty/corrupt folders.
- Empty `#EXT-X-ENDLIST`-only playlists are flagged explicitly.
